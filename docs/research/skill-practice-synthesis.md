# 四类写作 skill 的实践补充与中文适配

研究日期：2026-11-03。本文为设计研究，不是已经实现或验证的 skill。

## 阅读方法与证据边界

社区讨论用于发现具体困难、反例和实践线索；第一方作者文章、项目规范用于核对做法。投票数不代表效果验证。没有对照测量的“用户反馈变好了”不能写成框架降低认知负担的因果结论。

配套的 [社区来源记录](community-practices.md) 保存 HN、Reddit 帖子的细节。本文补充解释写作来源，并把研究转成候选规则。以下“建议”“推导”“自拟案例”均为本项目的设计判断，不是原作者原话。

## 解释写作的重点来源

### E1：解释的知识前提会过期，也可能前后矛盾

- 第一方：[Julia Evans，Patterns in confusing explanations](https://jvns.ca/blog/confusing-explanations/)，2021-08-19。
- 社区讨论：[HN，Patterns in Confusing Explanations](https://news.ycombinator.com/item?id=28254630)，2021-08-21。正文访问遇到 429；仅使用搜索可见的评论片段，不声称完整读过讨论。
- 作者举例：用旧版本管理工具解释 Git，未必适合从未用过那些工具的新读者；一边讲循环基础、一边默认读者了解内存分配，会造成前提错位。
- 候选规则：先写清具体读者已有的知识；检查每个推理环节是否依赖未交代的概念；请不熟悉该概念的人检验可理解性。
- 边界：专家复核仍然必要，但不能代替目标读者试读。这是作者经验，不是普遍有效的实验结论。

### E2：简单表达要保留搜索入口

- 第一方：[Julia Evans，How do you write simple explanations without sounding condescending?](https://jvns.ca/blog/2020/11/15/simple-explanations-without-sounding-condescending/)，2020-11-15。
- [HN 讨论](https://news.ycombinator.com/item?id=25112163)，2020-11-16，已读正文。
- 作者主张保留必要术语，帮助继续搜索；故事应与真实问题或系统行为有关。HN 评论者提醒，“很简单”“只需要”等措辞可能让遇到困难的人感到受挫。
- 候选规则：中文解释首次引入关键概念时，给准确术语、必要的英文检索词和具体含义；删除没有信息量的难易评价。
- 边界：不能据此全面禁用人称或类比；讨论中对这些写法存在分歧。

### E3：从实际代码中提炼例子

- 第一方：[Julia Evans，Write good examples by starting with real code](https://jvns.ca/blog/2021/07/08/writing-great-examples/)，2021-07-08。
- 作者做法：从自己写过的代码删去无关细节，得到独立示例；她举出把复杂 CSS 问题缩成很小例子的经历。
- 候选规则：优先从真实任务、真实故障或真实接口用法中提炼示例，并说明哪些条件为演示而简化。
- 边界：真实来源不保证例子适合教学；仍需检查复杂度和相关性。虚构示例可以使用，但应标明，不能伪装成生产经验。

## 四个 skill 应增加的能力

以下是结合来源后提出的设计建议，尚待行为测试。

| Skill | 应增加的写作决策 | 可观察的验收方式 |
| --- | --- | --- |
| Tutorial | 给定起点和固定路线；区分练习成果与学习目标；在关键阶段提供观察点；说明演示简化 | 在声明环境中从头执行；记录卡住的位置和结果偏差 |
| How-to | 以实际目标命名；说明适用与不适用条件；把读者必须作出的判断写成明确分支 | 用两个不同但适用的场景走查；读者能判断选哪条路径及何时完成 |
| Reference | 精确描述契约和边界；示例辅助查阅；区分默认、必填、可空、缺省行为等不同概念 | 抽取具体问题，检查能否独立找到答案，并与代码或可信来源核对 |
| Explanation | 从具体疑问建立因果链；显露知识前提；用反例界定模型，说明选择的条件 | 换一个条件后，检查读者能否运用解释推断结果；结论仍需技术复核 |

不把上述检查写成每次都要执行的重型流程。纯文字修改无需重跑整套系统；涉及步骤、接口或行为变化时，检查对应内容。无法执行时应报告未验证范围。

## 中文适配要在生成前发生

候选方法是先重建读者任务、概念关系和论证次序，再组织中文句子。不要先逐句翻译，再只修饰语气。以下均为自拟改写例，不来自真实产品。

### Tutorial：把抽象教学承诺变成可以观察的练习

- 弱：本教程将使你获得对于重试机制的理解。
- 改：这次练习会让请求先失败，再重试成功。运行后，观察日志中的两次请求记录。
- 保留教学设计中的学习目标；读者正文突出将做什么、看到什么。不能把“完成练习”直接当成“已经学会”。

### How-to：把省略的判断条件写出来

- 弱：适当地配置超时，然后应用它。
- 改：如果服务要求请求在两秒内结束，将请求超时设为 `2s`。保存配置后，按该服务的生效方式加载配置。
- 此处为句式演示；实际参数名、单位和加载方法必须由产品资料确认，不能凭例子补造。

### Reference：让读者区分几个容易合并的事实

- 弱：这个参数是可选的，用于控制重试。
- 改写时分别查证：省略参数时怎样处理、是否接受空值、合法范围、单位、默认值、何种错误触发重试。
- 材料没有给出的事实列为待确认项，不以“通常如此”填入参考文档。

### Explanation：补全因果，减少抽象名词堆叠

- 弱：通过对幂等性的实现来进行重复执行问题的规避。
- 改：请求超时后，客户端无法仅凭超时判断服务器是否已经处理请求。如果直接重试，可能重复创建订单。幂等键（idempotency key）可用于识别同一次操作；具体去重范围取决于接口契约。
- 这个例子示范“现象—缺失信息—风险—机制—边界”的组织方式，不是所有解释文档的固定模板。

中文适配还包括补足跨句指代、拆开多层限定、统一技术标识、保留检索词。它们是针对文本可用性的检查，不是关于中西方读者认知差异的实证结论。

## 不宜固化的规则

- 不把四类名称强制作为导航栏，也不强制每个主题写四篇。
- 不为保持类别纯度移走当前任务必需的前提、风险或简短解释。
- 不用“示例优先”替代完整的接口契约，也不以“参考应完整”为由塞入所有教学材料。
- 不把特定团队的成功经验提升为通用硬性流程。
- 不将 AI 模拟读者的结果写成真实用户测试结果。

## 后续验证建议

选一个资料齐全的主题，分别制作四类独立任务及其源材料。先看 skill 能否保持正确的读者承诺，再看中文是否自然、信息是否完整。增加反向任务：把参考误称为教程、给出缺失默认值的接口资料、要求对同一主题混合教学与查阅。检查模型能否识别冲突、限定范围并诚实处理未知。

研究材料按来源保存，安装包内只保留能改变写作决策的精炼规则和必要示例。每个 skill 的基础能力应自足，避免运行时依赖其他 skill。
